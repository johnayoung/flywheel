# Feature: Safe landing target (configurable, protected, non-checked-out base branch)

## Outcome
The worker lands a DONE task branch onto an explicitly configured base branch that it fetches fresh and updates without touching the operator's working tree; it refuses to land when the configured base is the operator's currently-checked-out branch; it survives a detached-HEAD operator checkout without exiting; and a base that has diverged such that the landing cannot fast-forward (post-rebase conflict or non-ancestor) becomes a recoverable, store-queryable terminal outcome rather than a silent stderr-only park.

## Background
Today `_phase_base` (worker.py:885-892) reads the base as `git rev-parse --abbrev-ref HEAD` and `_ff_merge` (worker.py:592-595) runs `git merge --ff-only` in `repo_root` — the operator's live checkout. Run the worker while sitting on `main` and finished task branches fast-forward straight into the operator's working branch, mutating files under their feet; on detached HEAD the worker `SystemExit`s before doing any work. No `git fetch` runs, so the base is whatever stale local ref happens to exist. The single recovery path (rebase + re-verify + one more FF) parks the worktree permanently on conflict with only a stderr line — invisible to anyone holding the store. The tacit requirement the audit surfaces: "lands onto the base" must mean a ref update that an external query can confirm landed the right base, on a host where the operator may be doing unrelated work — not "ran a merge in whatever directory the daemon started in." The CLAUDE.md invariant is verbatim: the worker never commits to the operator branch; landing is the SubmitStrategy's job; and nothing lands that was not verified against the exact base it lands on.

## Scope
### In scope
- A configured base-branch name for the `merge` strategy, read from `flywheel.toml` under `[submit] base` (parsed into `WorkPolicy.submit_base`, mirroring the existing `pr_base`/`submit_pr_base` pair — see SI-1 in the Decisions Log), distinct from the operator's checked-out branch; absent config keeps a defined default behavior.
- The worker fetching the base ref fresh from its remote before resolving and before landing, so it lands onto the up-to-date base rather than a stale local ref.
- Landing that advances the configured base branch ref WITHOUT requiring or mutating the operator's working tree, index, or `HEAD`.
- Refusing to land (and surfacing why) when the configured base equals the operator's currently-checked-out branch.
- Starting and running normally when the operator checkout is in detached-HEAD state (no `SystemExit`).
- A divergent base that cannot fast-forward after the existing rebase + re-verify path producing a terminal outcome that is queryable from the store (a recoverable status with a reason), not only a stderr log line.

### Out of scope
- The `pr` strategy's push/PR landing (already has its own `submit_remote`/`submit_pr_base`); this spec touches only the `merge` strategy's base.
- The agent-commits / git-identity gap (audit B2) and sandbox-setup default (B5) — separate specs.
- Auto-resolving merge conflicts, retry scheduling of a parked task, or any new conflict-resolution UX beyond making the outcome queryable.
- Multi-worker lease/clock correctness (audit M7), submodule/LFS handling (M5), Postgres read-path (M1).
- Any change to how `protected_paths` is matched (the existing merge-time path gate stays as-is).

### Must not regress
- The merge-time `protected_paths` gate still refuses to land a branch touching a protected pattern (worker.py:504-536).
- Submit-time re-verification still re-runs command graders against the rebased tree under the merge lock before the FF, and still refuses to land when a command grader fails (worker.py:538-577) — nothing lands unverified against the exact base it lands on.
- A zero-commit DONE branch is still treated as a legitimate no-op and cleaned up, not landed (worker.py:447-457).
- A pre-existing `flywheel.toml` with no base-branch key still loads without error (`load_policy` back-compat).
- The full existing suite (`uv run pytest`) still passes.

## Decisions Log (ADR-style: immutable, supersede — never edit)

### D-1: Base branch is an explicit config key on the `merge` strategy, defaulting to the operator's checked-out branch only when unset and not detached  (Status: Accepted)
- Context: `_phase_base` hardwires the base to the checked-out branch and dies on detached HEAD; the audit (B3) requires an explicitly configured base. The `pr` strategy already has `submit_pr_base`, but that is pr-only; the `merge` strategy threads `phase_base` from `_phase_base`.
- Decision: add a base-branch key under the existing `[submit]` table read by the `merge` strategy. When set, it is authoritative. When unset, fall back to the current checked-out-branch behavior for back-compat, EXCEPT that a detached HEAD with no configured base is a clear config error surfaced as a refusal (criterion 3 only guarantees no-crash WITH a configured base).
- Rejected: a brand-new top-level `[base]`/`[landing]` table (fragments config the `[submit]` table already owns); reusing `submit_pr_base` for both strategies (couples two independent landing strategies and would surprise pr users). Consequences: the merge and pr strategies now both have base-ish config under `[submit]`; the reconcile step (with specs 00027/00028) must keep the key names coherent.

### D-2: Refuse-to-land-into-checked-out-base is enforced at the landing seam, not only by branch-name comparison at startup  (Status: Accepted)
- Context: the cheapest fake for "refuse to merge into the checked-out branch" is a startup name-equality check that still runs `git merge` in `repo_root`, which mutates the working tree regardless. The real guarantee is that the operator working tree is never mutated by a landing.
- Decision: the landing must advance the base via a ref update that does not require the base to be checked out (e.g. update the base ref / merge into a ref the operator does not have checked out), and the refuse-when-equals-checked-out check is the belt; criterion 1 (operator tree byte-unchanged) is the load-bearing held-out guarantee, criterion 2 is the explicit refusal.
- Rejected: relying solely on a string compare of base vs `rev-parse --abbrev-ref HEAD` (gameable; does not protect the working tree if the merge still runs in `repo_root`). Consequences: the landing implementation can no longer assume it may `git merge` inside `repo_root`; it must update the base ref out-of-tree, which is also what makes detached-HEAD operation safe.

### D-3: Always fetch the base fresh before resolving and before landing  (Status: Accepted)
- Context: the audit notes no `git fetch` runs, so the worker lands onto a possibly-stale local ref; on a shared base this silently diverges.
- Decision: fetch the configured base from its remote before resolving the base SHA and before the FF/rebase, so the landing is always against the up-to-date base.
- Rejected: fetching only on FF failure (still lets the first lander overwrite a stale base); never fetching and documenting the caveat (the audit's exact complaint). Consequences: landing now requires a reachable remote for the base; a fetch failure must itself become a recoverable, queryable outcome rather than a crash (folded into criterion 5's "cannot land -> queryable terminal outcome" surface).

### D-4: A divergent/conflicting base produces a store-queryable terminal outcome, reusing existing lifecycle status vocabulary  (Status: Superseded by D-6 — the store-queryable outcome stays; the "reuse lifecycle status vocabulary" mechanism is replaced by the landing-parked domain event)
- Context: today a post-rebase conflict parks the worktree with only a stderr line (worker.py:478-502) — invisible to anyone holding the store, which breaks the "everything is queryable" goal.
- Decision: the park becomes a terminal outcome recorded in the store with a non-empty reason, queryable without reading stderr, reusing the existing lifecycle status/outcome vocabulary (not a new enum). The worktree is still preserved for forensics. Agent claims remain untrusted; the harness owns the transition.
- Rejected: inventing a new status enum member (cross-cutting churn, and the data taxonomy already distinguishes authoritative state from telemetry); leaving it as stderr-only (the audited defect). Consequences: criterion 5 reads the store, not the log; the exact status/reason surface is a shared invariant the landing layer and spec 00027 must agree on.

### D-5: Reconciliation (2026-06-17) — canonical key SI-1, and 00027 lands before 00026 on the shared `_submit` seam  (Status: Accepted)
- Context: the cross-spec reconcile read 00026 alongside 00027 (shared `worker.py` `_submit`/landing path) and 00028 (shared `_INIT_POLICY_TAIL` + `WorkPolicy`). Two divergence risks: (a) an unnamed merge-base key could collide with 00028's `[sandbox]` block or duplicate 00026's own work, (b) both 00026 and 00027 edit `_submit`, with no declared order.
- Decision: (1) The merge-base key is canonically `[submit] base` -> `WorkPolicy.submit_base` (SI-1), mirroring `pr_base`/`submit_pr_base`; default `None` means "fall back to the checked-out branch" (back-compat), and a detached HEAD with no configured `submit_base` is the surfaced config error of D-1. (2) **00027 is a prerequisite of 00026** (SI-6): 00027 rewrites the HEAD of `_submit` (the porcelain dirty-tree-vs-no-op classification at `worker.py:439-457`) and the worktree provisioning identity; 00026 then rewrites the TAIL (`_ff_merge`/`_phase_base`/base-fetch/divergent-base park at `worker.py:468-502, 592-595, 885-892`). Landing 00027 first means 00026 inherits the green classification gate rather than racing it. The two failure surfaces stay distinct: 00027's uncommitted-work marker is git-observable on the preserved worktree; 00026's divergent-base outcome is store-queryable via the lifecycle status/reason vocabulary. Neither reads the other's surface.
- Rejected: ordering 00026 first (its TAIL edits would conflict with 00027's HEAD rewrite of the same function, and 00026's no-op/uncommitted assumptions would be the pre-00027 ones); a fresh top-level base table (re-litigated in D-1); leaving the order undeclared (the #1 divergence risk this reconcile exists to kill).
- Consequences: `/fw-plan` for 00026 must emit a cross-spec prerequisite on 00027's `_submit`-classification task. If the two land in one phase, 00026's landing-layer task carries 00027's submit-classification task as a `prerequisites` entry.

### D-6: Divergent-base park is the SAME store landing-parked domain event (park-kind=divergent-base), NOT a reused lifecycle status — supersedes D-4  (Status: Accepted, 2026-06-17)
- Context (operator decision 2026-06-17): "parked at submit" must be ONE unified, queryable outcome across BOTH park types — 00026's divergent-base park and 00027's uncommitted-work park — so an operator (and a future cross-task query) reads one timeline of landing failures, not a lifecycle-status row for one and a git marker for the other. Reading `flywheel_core.events` / `event_serde.py` and the store ledger (`append_domain_event` / `list_domain_events`, `store_protocols.py:333-364`) confirmed each event is stored as opaque JSON (`kind` discriminator + `payload_json`), and that the identity-fold branch of `events.apply` already admits audit-witness events that record a fact without mutating lifecycle state (`Unblocked`, `RetryScheduled`, `GraderEvaluated`, `CommandApplied`).
- Decision: the divergent-base park is recorded by appending the SAME landing-parked domain event defined and owned by 00027 (SI-12 there / SI-7 in 00027), with its `park_kind` field equal to `divergent-base` and a non-empty `detail` reason, queryable via `list_domain_events(run_id)`. The canonical contract (do NOT redefine it — 00026 CONSUMES it): `DomainEventKind.LANDING_PARKED` (wire tag `landing_parked`), a frozen `LandingParked(_DomainEventBase)` carrying `park_kind: str` and `detail: str = ""`, folded by the identity branch of `events.apply` (no lifecycle-state mutation), round-tripped by `event_serde.py`, persisted on the existing opaque-JSON `events` ledger. NO new lifecycle `Status` is added; the run stays terminal `DONE`; the worker performs NO lifecycle transition — it appends one audit-witness domain event via `append_domain_event` (`store_protocols.py:357`). Because the ledger is generic opaque-JSON storage, the new kind is additive and `schema_version` stays at 12 (SI-9 holds — flag loudly if reading the code proves a migration is unavoidable). `flywheel_core.events` stays pure (a frozen dataclass with primitive fields, no json/pathlib/io). The worktree is still preserved for forensics.
- Supersedes: **D-4** ("store-queryable terminal outcome, reusing existing lifecycle status vocabulary"). D-4's text is retained unedited and is now superseded — no lifecycle `Status`/`Outcome` is reused or added; the outcome is the landing-parked domain event on the ledger.
